# Issue and PR evidence

Use repository templates when present. Otherwise include the following information without forcing empty sections.

## Finding/issue

- Outcome: one user-visible or engineering result
- Severity and affected roles/platforms
- Starting state and exact reproduction steps
- Expected behavior, with source link or established product rule
- Actual behavior
- Evidence: screenshot/recording, console/log output, or failing test
- Duplicate search performed
- In scope and out of scope
- Dependencies, blockers, and overlap with open PRs
- Acceptance criteria
- Automated checks and manual states required
- Proposal-only or protected boundary when applicable

Do not create an issue for a vague dislike. A flaky issue needs repeated evidence or an explicit investigation outcome.

## Pull request

- Linked issue and concise scope
- Why the change fixes the observed problem
- Material files/behavior changed
- Automated commands and exact results
- Primary-platform journey and states exercised
- Screenshots inspected and comparison target
- Runtime/console findings
- Independent reviewer and findings addressed
- Unavailable checks and remaining risk
- Expected overlap or rebase risk with queued PRs

Keep screenshots temporary unless the repository explicitly requests committed baselines or documentation evidence.
